A0

How to approach the room

Framework

Every mobile system design question — chat app, image loader, downloader — collapses into the same four-beat structure. Learn the beats once, reuse them everywhere.

Fig. A0.1 — interview flow, left to right
Clarify first

Ask about scale, offline behavior, target platforms and battery/data budgets before drawing a single box.

Mobile ≠ server

Battery, flaky networks, background‑execution limits and finite storage are constraints server design rarely faces.

Interviewer signals to watch for
  • They keep steering toward one component — that's your deep‑dive cue, stop broadening the design.
  • Silence after your high‑level diagram usually means "go deeper," not "you're done."
  • Always state a trade‑off out loud (e.g. "cache‑aside is simpler but risks stale reads") — the reasoning is graded, not just the box diagram.
A1

Caching

Building block

The most-reused building block in mobile design: a fast, unreliable memory tier in front of a slower, durable disk tier, in front of the network.

Fig. A1.1 — read path checks memory → disk → network, populating on the way back
Eviction

LRU drops the item unused longest; LFU drops the item used least often. Pair with a TTL or size cap.

Write strategy

Cache‑aside (app manages both) is the default; write‑through trades latency for consistency.

Mobile‑specific gotchas
  • Respond to onTrimMemory / memory‑warning callbacks — a cache that ignores them gets the whole process killed.
  • Disk cache needs a hard size cap; mobile storage is finite and shared with the rest of the OS.
  • Cross‑process apps (widgets, share extensions) need the disk tier to be the shared truth — memory caches don't cross process boundaries.
A2

Sync & networking

Building block

Offline‑first apps write locally first and treat the network as an eventually‑consistent background job, not a blocking dependency.

Fig. A2.1 — write-local, sync-later, with a gated retry loop
Backoff

Exponential backoff plus jitter stops every client retrying in lockstep and hammering a recovering server.

Conflicts

Last‑write‑wins is the simple interview answer; CRDTs or vector clocks preserve intent for collaborative data.

Battery-aware scheduling
  • Batch outbox items into one request instead of one round‑trip per change — radio wake‑ups are the real battery cost, not bytes.
  • Defer non‑urgent sync to platform schedulers (WorkManager, BGTaskScheduler) so the OS can coalesce it with other apps' network activity.
  • Prefer cursor‑based pagination over offset — stable under concurrent writes and cheaper to resume after a dropped connection.
A3

Image loading pipeline

Building block

The Glide / Coil / SDWebImage shape: a request keyed by URL and target size, resolved through caches before ever touching the network.

Fig. A3.1 — miss cascades right, hit short-circuits and renders immediately
Downsample

Decode to the target view's pixel size, never full resolution — the #1 cause of list‑scrolling OOM crashes.

Cancellation

Tag each request with its view; when a row is recycled, cancel or ignore the stale callback so the wrong image never lands.

Extras interviewers like to hear
  • Bitmap pooling — reuse decoded buffers of the same size instead of allocating fresh ones per scroll frame.
  • Priority: visible viewport first, prefetch just below the fold, cancel everything scrolled far out of view.
  • Placeholder → low‑res blur → full image gives a perceived‑performance win almost for free.
A4

File downloader

Building block

Large, resumable transfers that must survive app kills, network drops, and a user who backgrounds the app mid‑download.

Fig. A4.1 — parallel ranged chunks merge into one verified, atomically-placed file
Resume

Persist bytes‑received per chunk locally so a relaunch resumes with Range headers instead of restarting.

Atomic finish

Write to a temp path, verify, then rename — a crash mid‑write never leaves a corrupt file at the final path.

Platform mechanics
  • Hand the transfer to a background transfer service (WorkManager, URLSession background config) so it survives app suspension.
  • Cap concurrent chunk downloads — more parallelism helps only up to the link's actual bandwidth‑delay product.
  • Surface pause / resume / retry as first‑class states in local storage, not just in‑memory flags.
A5

Chat application

Feature case

A messaging client is caching, sync and offline-first patterns combined, plus a persistent connection and delivery-state tracking.

Fig. A5.1 — write local → send over socket → ack propagates delivery state back
Local‑first

Message gets a client‑generated UUID and lands in the local DB instantly — the UI never waits on the network.

Fallback path

OS‑level push (FCM/APNs) wakes a backgrounded recipient once the socket is suspended by the platform.

Deep-dive topics interviewers reach for
  • Media messages: send a thumbnail inline, queue the full asset through the file‑downloader pattern from A4.
  • End‑to‑end encryption (Signal‑protocol shape) — mention key exchange and that the server only ever relays ciphertext.
  • Local full‑text search index over message history, since the server can't search what it can't read.
  • Pagination of history: cursor‑based, fetched backwards from "now," cached to disk per conversation.
A6

Stories (Instagram-style)

Feature case

Short-lived, ordered, media-heavy content — the interesting problems are prefetch timing and expiry, not the data model.

Fig. A6.1 — the viewer always stays one story ahead of the cache
Prefetch window

Fetch story N+1's media during story N's playback so the tap‑next transition never shows a spinner.

Expiry

A simple expiresAt field filters feeds and drives a background job that purges cached media past TTL.

UI state machine & telemetry
  • Each segment is its own progress‑bar timer: tap‑hold pauses it, release resumes, timeout auto‑advances.
  • "Seen" events are batched client‑side and flushed periodically — one network call per view would drain both battery and data.
  • Preload only images/short clips eagerly; long‑form video within a story streams instead.
A7

Field cases: Facebook & WhatsApp

Real-world

Two production apps, two very different priorities — one optimized for feature velocity at massive scale, one optimized for privacy and offline resilience.

Fig. A7.1 — velocity architecture vs. minimal-trust architecture
Facebook

Independent feature modules behind a shared DI container let teams ship and A/B‑test in parallel without one monolithic build.

WhatsApp

The phone's database is canonical; the server is deliberately kept "dumb" so it has as little user data as possible to protect or leak.

What to borrow from each in an interview
  • From Facebook: feed virtualization + prefetch-ahead pagination generalizes to any long scrolling list.
  • From WhatsApp: "client owns the truth, server relays" is a strong answer whenever privacy or offline resilience is emphasized.
  • Multi‑device sync (WhatsApp companion devices) is a good deep‑dive if the interviewer pushes on "what changes with two phones."
